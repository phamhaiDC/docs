🎯
Nguyên nhân gốc: VM bị khóa CPU ở base clock 2.70 GHz (không turbo) và chia thành 2 NUMA node. CPU vật lý là Intel Xeon Platinum 8558P — chip top-tier, turbo tới 4.0 GHz — nhưng hypervisor không cho VM boost, khóa cứng ở 2.70 GHz. Các truy vấn của RKeeper (tìm khách theo SĐT, parse REGISTER_CODE) chạy đơn luồng, phụ thuộc 100% vào tốc độ 1 core, nên bị chậm ~32% so với server có turbo. RAM và IOPS không phải nguyên nhân — đều còn dư nhiều.

⚠

Cùng loại truy vấn khi kết nối tới một SQL Server khác thì chạy nhanh hơn hẳn. Nghi vấn ban đầu: VM thiếu tài nguyên (CPU/RAM/IOPS) và/hoặc database CVL_SKYMONITOR ghi liên tục gây tranh chấp.

1. Base clock pinned: Task Manager hiển thị Speed = 2.70 GHz = đúng Base speed. Chip Xeon 8558P turbo được tới 4.0 GHz nhưng hypervisor không truyền turbo vào guest. Truy vấn RKeeper đơn luồng lẽ ra chạy 4.0 GHz nay bị ép 2.70 GHz → chậm ~32%.

2. Cross-NUMA: VM cấu hình 2 socket × 4 vCPU tạo 2 NUMA node. SQL chia buffer pool 2 phần (node 0: 1,048 MB / node 1: 1,671 MB). Khi query chạy ở socket này nhưng data nằm ở RAM socket kia, phải truy cập qua liên kết chậm hơn (cross-NUMA latency). Cấu hình tối ưu cho VM 8 vCPU là 1 socket × 8 core (1 NUMA node).

Phần cứng host mạnh (Xeon Platinum 8558P), RAM và IOPS đều dư. Nút thắt thật là VM bị khóa base clock 2.70 GHz (không turbo) kết hợp chia 2 NUMA node — làm chậm các truy vấn RKeeper đơn luồng. Giả thuyết ban đầu đúng ở hướng "VM cấu hình chưa tối ưu / over-resource", nhưng cụ thể nằm ở tầng CPU clock + topology, không phải thiếu RAM/IOPS. Đòn bẩy lớn nhất là làm việc với VNG Cloud về turbo và cấu hình 1 socket (bước 1–2), song song với việc tách workload nền và đưa Feature Request tới UCS để giảm chi phí CPU của query tận gốc.
